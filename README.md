# 洗衣房 · 布草收发与洗涤批次管理系统

酒店洗衣房 / 布草间的日常台账系统：**布草台账**、**污染封存**、**洗涤批次**、**回洗追差**、**楼层收发**、**报损赔付**。

## 技术栈

Spring Boot 3.3（Java 17）+ MySQL 8.0 + Redis 7 + Vue 3 + Element Plus + Vite + nginx，全栈 `docker compose` 一键启动。

## 启动

```bash
./start.sh              # 等价于 docker compose up -d --build
```

| 入口 | 地址 |
| --- | --- |
| 前端页面 | http://127.0.0.1:8212/ |
| 后端接口 | http://127.0.0.1:8312/api/ |
| MySQL | 127.0.0.1:3512（库 `laundry_room`） |
| Redis | 127.0.0.1:6512 |

## 停止

```bash
docker compose down       # 保留数据卷
docker compose down -v    # 连数据卷一起删，下次启动重新灌种子数据
```

## 业务模块

### 1. 布草台账（`linen`）

布草编号 `LN-xxx` 全库唯一，分 `床单 / 被套 / 枕套 / 浴巾 / 地巾` 五类，各带规格。
每件布草记「在库件数」和「预警线」，在库低于预警线时在列表里高亮提醒。
状态为 `在用 / 停用`。停用不是「在库为零」就能落：**先把在途单据清干净**——
没走到 `已完成` 的洗涤批次、已送出没收回的楼层单、待确认的报损、未结案的回洗追差、
没解除的污染封存，任何一张挂着都停不了，报错会说清卡在哪一张单。
停用和收工抢同一把台账行锁，只成一个：要么还在用、收工按回洗件数加库，
要么停用成立、收工被挡住——停用档案上不会再长出可领用件数。

- 页面：布草台账（`/linens`）
- 接口：`GET /api/linens`、`POST /api/linens`、`PUT /api/linens/{id}`

### 2. 污染封存（`contaminated_seal`）

传染病房 / 污物间退下来的布草走这一桩感染控制流程，封存单号 `QZ-xxxx`。

- **开单一次写清**：哪件在用布草、涉及楼层、封存件数、发现时刻、发现人。
- **封存即扣库**：单子落下的同一事务里就把封存件数从 `linen.stock` 扣掉，
  关掉页面再打开台账，在库已经少这么多。
- **同一件同时只能一桩未解除**：两个人抢着开，行锁串行化，只成一张；
  另一张当场报错，明确是「在库不够」还是「已有未解除封存占着」。
- **解除前必须挂专洗**：`POST /api/seals/{id}/special-wash` 挂出的批次洗法固定为 `专洗`，
  件数由服务端取封存「还未解除件数」，恰好相等；**专洗不走在库够不够的老校验**
  （它用的就是封存已扣下的件数）。
- **专洗走完状态机到 `已完成` 才能解除**：`POST /api/seals/{id}/release`
  同一事务里把件数还回在库；专洗没完成，封存解不了、件数回不了可领用。
- 专洗没完成时：楼层收发按扣完后的在库校验，**不能把封存件当干净布草送出**；
  报损**确认**同样被拦住；常规洗涤只认当下在库，封存件进不去常规批次；
  专洗也不能从常规开单入口混开。

- 页面：污染封存（`/seals`）
- 接口：`GET /api/seals`、`POST /api/seals`、`POST /api/seals/{id}/special-wash`、`POST /api/seals/{id}/release`

### 3. 洗涤批次（`wash_batch`）

批次号 `WB-xxxx` 全库唯一。一个批次 = 某件布草送出去洗一批。
状态机 `待洗 → 洗涤中 → 待烘干 → 已完成`，每次只能往前走一步。
写入时校验：送洗件数不能超过在库；预计回洗日期不能早于送洗日期；
**同一件布草同一天只能开一个常规批次**；停用的布草不能送洗。
洗法有 `常规 / 强化 / 专洗`：**专洗只能由污染封存单挂批**，不占用可领用在库，
其余两种只认当下在库（封存扣掉的件数开不进常规批次）。

**送洗即出库**：常规 / 强化批次一开，送洗件数当场从在库扣掉，洗完才回来。
**收工按实际回洗件数回库**：回洗少于送洗时，只把回来的件数加回在库，
短少的几件当场挂一张**回洗追差**（见下），追差没结案，在库就不能按送洗全额涨。
两个人同时点收工，批次行锁串行化只成一个；后到的报错会说清是
「追差已经挂着没结案」还是「这张批次还没到已完成」。
**布草已停用的批次收工直接被挡住**：停用档案上不能再长出可领用件数，要收工先启用。

- 页面：洗涤批次（`/batches`）
- 接口：`GET /api/batches`、`POST /api/batches`、`POST /api/batches/{id}/advance?action=`（`done` 可带回洗件数 / 责任 / 发现人）

### 4. 回洗追差（`wash_shortage`）

回洗车少件就走这里：送出去八十件、只回来七十二件，短少的八件挂成追差单 `ZC-xxxx`。
收工当场必须写清：**短少件数、布草、责任楼层或工序、发现人**，一样不能少。

- **结案前不进在库**：短少件数从收工那一刻起就扣在可领用在库之外，
  楼层收发只认在库，自然拿不到这几件当干净布草送。
- **一张已完成批次同时只挂一张未结案追差**：数据库唯一索引兜底，并发收工也只成一张。
- **结案只两条路**：
  - `补回入库`：短少件数找回来了，当场加回在库，追差结案；
  - `转报损`：生成 `待确认` 报损单（带来源标记），**报损确认那一刻追差才结案**——
    确认前追差仍未结案，件数还是不进在库；确认时不再从在库扣第二遍
    （短少件数收工时就没能回库）。

- 页面：回洗追差（`/shortages`）
- 接口：`GET /api/shortages`、`POST /api/shortages/{id}/replenish`、`POST /api/shortages/{id}/to-loss?reason=`

### 5. 楼层收发（`floor_issue`）

某天某个楼层领走多少件布草、后来收回多少件。写状态 `已送出 / 已收回`。
写入时校验：送出件数不能超过在库（已扣除污染封存件数）；**同一件布草同一个楼层同一天只能登记一条**；
停用布草不能往楼层送。收数时 **收回件数不能多过送出的件数**，收回后这条就锁住不能再收。

- 页面：楼层收发（`/issues`）
- 接口：`GET /api/issues`、`POST /api/issues`、`POST /api/issues/{id}/giveback?backQty=`

### 6. 报损赔付（`linen_loss`）

洗坏、丢掉、污损洗不掉的都从这里走，原因分 `破损 / 丢失 / 污损`，可记责任楼层。
写入时校验：报损件数不能超过在库；**同一件布草同一天只能报一次**。
状态 `待确认 → 已确认`；**确认时才真正扣减在库件数**，扣完不能再确认第二次。
**确认时若这件布草还有未解除的污染封存（专洗未完成），拒绝扣减。**
从回洗追差转进来的报损单带来源标记：确认时只走状态、联动追差结案，
不再从在库扣第二遍（短少件数在批次收工时就没能回库）。

- 页面：报损赔付（`/losses`）
- 接口：`GET /api/losses`、`POST /api/losses`、`POST /api/losses/{id}/confirm`
